# x86_64

[프로젝트 소개](../../README.md) · [공통 시스템 구조](../architecture.md) · [Pi 5](raspberry-pi-5.md)

BIOS에서 부팅하는 x86_64 포트입니다. QEMU의 IDE/ATA PIO와 q35/AHCI 경로를
지원하며, 64MiB FAT32 디스크 이미지 `img64/mowkow64.img`를 만듭니다.
셸 명령은 저장소 루트에서 실행합니다. 커널 소스의 짧은 경로는
`64bit/src64/` 기준이며, 빌드·앱·도구 경로는 저장소 루트 기준입니다.

## 준비물

GNU 크로스 툴체인을 사용합니다. 기존 개발 환경은 GCC 13.1.0, binutils 2.40과
Ubuntu 24.04.4 LTS(WSL2)입니다. 아래 설치 예시는 해당 버전을 기준으로 합니다.

* 아키텍처: `x86-64`
* 툴체인:

    * `x86_64-elf-gcc`, `x86_64-elf-ld`, `x86_64-elf-objcopy`
    * `nasm`
    * `qemu-system-x86_64`
    * `python3` (이미지 생성 도구)

### 크로스 툴체인 설치 방법

아래 명령은 binutils와 GCC 소스 압축 파일이 준비되어 있다고 가정합니다.

```bash
sudo apt install build-essential bison flex libgmp-dev libmpc-dev libmpfr-dev texinfo
```
```bash
export PREFIX="$HOME/opt/cross"
export TARGET=x86_64-elf
export PATH="$PREFIX/bin:$PATH"
```
```bash
# binutils 2.40
tar xf binutils-2.40.tar.xz && mkdir build-binutils && cd build-binutils
../binutils-2.40/configure --target=$TARGET --prefix="$PREFIX" \
    --with-sysroot --disable-nls --disable-werror
```
```bash
make -j$(nproc) && make install && cd ..
```
```bash
# gcc 13.1.0
tar xf gcc-13.1.0.tar.xz && mkdir build-gcc && cd build-gcc
../gcc-13.1.0/configure --target=$TARGET --prefix="$PREFIX" \
    --disable-nls --enable-languages=c --without-headers
make -j$(nproc) all-gcc all-target-libgcc
make install-gcc install-target-libgcc
```

### 툴체인 경로 지정

```bash
make x86_64 X64_CC=/path/to/x86_64-elf-gcc X64_LD=/path/to/x86_64-elf-ld
```

## 빌드와 실행

```bash
make x86_64         # img64/mowkow64.img 만들기
make run64          # IDE로 실행 (ATA PIO 경로)
make run64-ahci     # q35 + AHCI로 실행 (AHCI 경로)
make parity64       # 머꼬 병행 검사 (호스트 CPython과 견주기)
make parity64-ahci  # 같은 검사를 q35 + AHCI로 실행
make test64-qemu    # 복제 이미지에서 머꼬 + ktest/mtest/wtest IDE 회귀 검사
make test64-qemu-ahci # 같은 회귀 검사를 q35 + AHCI로 실행
make clean64        # build64/, img64/ 지우기(rm)
```

QEMU 회귀 검사는 원본 이미지를 임시 복제하고 검사 종료 후 복제를 정리합니다.
`ktest --auto`의 키 입력과 raw 종료 후 cooked 복귀, `mtest` 재실행,
`wtest HUGE`의 쓰기·읽기와 재부팅 후 `wtest --verify-huge`의 전체 내용·크기를
고정 출력과 종료 코드로 판정합니다. COM1 로그는
`/tmp/mowkow-regression-{ide,ahci}-{parity,apps,reboot}.log`에 남습니다.
Pi 5 실행이나 모든 앱·저장장치 실패 경로를 검증하는 검사는 아닙니다.

일반 빌드는 부팅 중 FAT32에 테스트 파일을 쓰지 않습니다. 저장장치 쓰기
smoke test가 필요한 폐기 가능한 이미지에서만 clean build로
명시적으로 켭니다.

```bash
make clean64
make BOOT_TEST64=1 x86_64
```

일반 빌드로 돌아올 때도 `make clean64` 뒤 `make x86_64`로 다시 빌드합니다.

`make help`를 치면 32bit와 64bit 명령이 함께 출력됩니다.

`run64`와 `run64-ahci`는 같은 이미지를 서로 다른 저장 장치 경로로 띄웁니다.
q35에는 레거시 IDE가 없으므로, 저장 장치 쪽을 수정했다면 두 명령어를 모두 시도해 봐야 합니다.

## 부팅이 이상할 때

콘솔이 뜨기 전 단계에서는 화면에 아무것도 출력할 수 없습니다.
따라서 커널이 진행 상황을 COM1(시리얼)로 내보냅니다.
QEMU에 `-serial stdio`를 붙이면 아래와 같이 확인할 수 있습니다.

```
Mowkow OS x86_64 kernel64_main
fpu smoke=2
disk transport=ata part-base=0
fat32 files=8
sheet64 smoke=ok
keyboard64 smoke=ok
hangul64 smoke=ok
hangul font=loaded
```

위 출력은 읽기 전용 자체 점검입니다. `BOOT_TEST64=1` 빌드는
`destructive boot tests=enabled` 뒤에 `fat32 write`, `fat32 chain`,
`fat32 lfn` 결과도 출력하고 테스트 파일을 생성하거나 갱신합니다.
마지막 진단과 panic 단계로 초기화 실패 위치를 확인합니다.

## 시스템 구조

### 부트 시퀀스

x86_64는 다음 BIOS 부트 경로를 사용합니다.

부트 섹터 512바이트 안에 FAT32 BPB와 롱 모드 진입 코드를 함께 넣을 수 없어 1단계는 BPB와 디스크 읽기만 담고 나머지를 2단계로 넘겼습니다.

```
boot64.asm (1단계, 부트 섹터 512B, LBA 0)
  └ FAT32 BPB 내장, int 13h AH=42h로 2단계 로더 읽기
    └ loader64.asm (2단계, 0x8000)
      └ 커널 읽기(LBA 32), VBE 0x4103, boot_info 수집, A20
        └ 보호 모드 → 페이지 테이블, PAE, EFER.LME, CR0.PG → 롱 모드
          └ _start (asmfunc64.asm)
            └ 스택 설정, .bss를 0으로 채움
              └ kernel64_main (kernel64.c)
```

* `_start`가 `.bss`를 직접 0으로 채우는 이유

    * 로더는 항상 `KERNEL64_SECTORS × 512`바이트를 통째로 디스크에서 메모리로 옮기는데, 그 범위가 `.bss`의 적재 주소를 넘어서기 때문에 `.bss`를 미리 0으로 채워놓지 않으면 해당 자리에 0이 아니라 디스크에 있던 내용이 들어옵니다.

* BIOS 제약

    * `int 13h AH=42h`는 한 번에 128섹터(64KiB)까지만 읽습니다. 더 요청하면 실패합니다.
    * `int 0x13`은 EAX를 보존하지 않습니다(SeaBIOS가 내부 LBA 계산에 사용). 그래서 진행 중인 LBA 값을 레지스터가 아니라 메모리에 둡니다.

`kernel64_main` 초기화 순서

```
1. GDT/IDT, FPU
2. 메모리 관리자
3. 저장 장치 전송 계층 (AHCI 또는 ATA)
4. FAT32
5. 한글 글꼴 (디스크에서 H04.FNT 읽기)
6. 팔레트, 콘솔
7. 태스크, 이벤트 큐, 콘솔 태스크 시작
8. 타이머(PIT), PIC
9. sti
10. 키보드, 마우스
11. 이벤트 루프
```

`kernel64.c`는 초기화 순서와 최상위 이벤트 라우팅을 담당합니다.
COM1 진단·글꼴 적재는 `arch/x86_64/boot_diag64.c`, 자체 점검은
`arch/x86_64/boot_smoke64.c`로 분리되어 있습니다. 필수 초기화 실패는
단계와 오류를 기록하고 정지하며, 마우스 실패는 진단 후 계속 진행합니다.
파괴적인 FAT32 쓰기 점검은 `BOOT_TEST64=1` 빌드에서만 실행합니다.

### 메모리 배치

커널은 1MiB에 링크하며, 고정 사용자 이미지 창을 일반 메모리 풀에서 제외합니다.

| 구간 | 용도 | 비고 |
|-|-|-|
| `0x00100000` | 커널 이미지 (.text/.rodata/.data/.bss) | `kernel64.ld`가 1MiB에 링크 |
| `0x00400000`-`0x00800000` | 유저 이미지 창 | 메모리 풀 바깥. `app64.ld`가 모든 앱을 `0x400000`에 링크 |
| `0x00800000`-`0x20000000` | 일반 메모리 풀 (`memman64`) | `MEMMAN64_EARLY_START` ~ `_END` |

현재 넓은 user-accessible 아이덴티티 매핑을 공유하므로 Ring 3 앱도 커널
메모리에 직접 접근할 수 있습니다. syscall 포인터 검사는 주소 공간 격리를
제공하지 않으며, 신뢰된 내장 앱만 실행하는 모델입니다.

### 태스크와 사용자 모드 진입

`arch/x86_64/platform64.c`는 IRQ 상태를 RFLAGS로 저장·복원하고,
`kernel/asmfunc64.asm`의 `context_switch64`로 스택을 전환합니다.
전환의 골격은 다음과 같습니다.

```asm
context_switch64:          ; rdi = 현재 문맥, rsi = 다음 문맥
    push rbx / rbp / r12 / r13 / r14 / r15   ; 콜리 세이브 레지스터만
    mov [rdi], rsp                            ; 현재 rsp 저장
    mov rsp, [rsi]                            ; 다음 rsp 로드
    pop r15 / r14 / r13 / r12 / rbp / rbx
    ret                                       ; 새 스택의 복귀 주소로
```

`enter_user_mode64`는 SS/RSP/RFLAGS/CS/RIP를 쌓고 `iretq`로 Ring 3에 진입합니다.
`SYS_EXIT`과 사용자 예외 종료는 저장된 커널 RSP를 복원해 실행 호출자로 돌아옵니다.

| syscall ABI | 값 |
|-|-|
| 진입 | `int 0x80` |
| 번호 | `rax` |
| 인자 1~6 | `rdi/rsi/rdx/r10/r8/r9` |
| 반환값 | `rax` (오류는 음수) |
| ELF machine | `EM_X86_64` |

번호와 각 연산의 의미는 [공통 syscall 계약](../architecture.md#프로세스와-syscall)을 따릅니다.

### 화면과 입력

VBE 800x600 8bpp 선형 프레임버퍼를 사용합니다. 행 pitch는 가로 픽셀 수와
다를 수 있으며 공용 framebuffer 계층에서 검증합니다. x86 VBE backend의
cache clean hook은 no-op입니다.

PIT가 100Hz 틱을 제공하고 PIC가 IRQ를 전달합니다. PS/2 키보드·마우스 이벤트는
`kernel64.c`의 이벤트 루프에서 처리합니다. GUI가 마우스와 F11을 먼저 처리하고,
나머지 키는 포커스가 있는 콘솔 태스크로 전달합니다.

### 저장 장치와 디스크 배치

`block64.c`는 AHCI probe 성공 시 AHCI를 선택하고, 실패하면 ATA PIO를 사용합니다.
공용 FAT32·캐시 계층은 전송 방식에 의존하지 않습니다.

```
LBA 0           부트 섹터 (FAT32 BPB)
LBA 1           FSInfo
LBA 6, 7        부트 섹터/FSInfo 사본
LBA 8..23       2단계 로더
LBA 32..1023    커널 이미지 (예약 영역)
LBA 1024        FAT #1
LBA 2025        FAT #2
LBA 3026        데이터 영역, 클러스터 2 = 루트 디렉터리
```

2단계 로더와 커널이 예약 영역에 있으므로 커널이 커져도 파일 시스템이 밀리지 않습니다.
이 배치는 `64bit/tools/mkfat32_64.py` 한 곳에만 적혀 있고, Makefile과 부트 섹터가 해당 파일에서 값을 읽습니다.
배치를 바꿔야 하면 Makefile이나 BPB를 직접 고치지 말고, `64bit/tools/mkfat32_64.py`를 고쳐야 합니다.

## 사용상 주의와 한계

- 나노로 저장한 파일은 이미지 파일에 실제로 남습니다. `make clean64` 뒤 다시 빌드하면 새로 저장된 파일이 사라지니 주의하세요.
- 저장 장치 쪽을 수정했다면 `make run64`와 `make run64-ahci`를 모두 확인해야 합니다. q35에는 레거시 IDE가 없어 두 명령이 실제로 서로 다른 코드를 지나갑니다.
- 커널 크기 상한은 `64bit/mk/x86_64.mk`의 `KERNEL64_SECTORS`(현재 960섹터)입니다. 넘으면 링크 직후 빌드가 멈춥니다. 예약 영역이 1024섹터이고 커널은 LBA 32부터라 992섹터까지는 파일 시스템을 밀지 않고 올릴 수 있습니다.
- 머꼬 소스는 `64bit/py64/`에 두면 이미지 루트로 들어갑니다. 다만 파일을 지웠을 때는 make가 알아채지 못하니 `rm img64/mowkow64.img` 뒤에 다시 빌드하세요.
- AHCI는 사용 가능한 첫 포트만 사용하며 NCQ 없이 한 번에 명령 하나를 폴링합니다.
- ATA PIO는 명령당 1섹터를 전송합니다.
- `make test64-qemu`와 `make test64-qemu-ahci`는 전체 앱·장치 실패 경로를 포괄하지 않습니다.
